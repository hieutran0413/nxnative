# TOTK 60 fps on A16-class devices

Status: implementation in progress; the narrow BC4 3D path is implemented and host-builds, but integration/gameplay correctness, memory pressure and acceptance evidence remain open.
Owner: NX Native graphics/runtime
Updated: 2026-10-26

## Goal

Reach a 16.67 ms frame-time budget and stay below 3072 MiB during representative gameplay on the Mac simulation. Keep game data, UI, alpha, and color correct. Reduce 3D render scale before texture fidelity. Device thermals, battery, and sustained 60 fps require user-provided logs from a sideloaded unsigned IPA on real A16 hardware.

## Evidence at this milestone

### Milestone audit — A16 Pro and below (2026-10-26)

**Current gate: P0 correctness and memory qualification; not accepted.** Available evidence does not support a 60 fps preset for A16 Pro or older. A matched 20-second route at scale 0.5 now confirms both BC and ASTC-disabled no-BC gameplay, but both retain a strong green color cast and exceed memory/frame targets: 3789/4887 MiB peak footprint and 36.59/36.52 ms gameplay frame p95, respectively. The no-BC route reached 16.65 ms GPU p95, so GPU time alone does not explain its ~36 ms frame p95; the logged display interval is 33.33 ms. Both used a raised diagnostic watchdog and fail the fixed 3072 MiB ceiling. Previous confirmed no-BC gameplay diagnostics at render scales 0.30–0.35 were also visibly corrupted, peaked at 3950–4210 MiB and measured frame p95 at 20.18–20.98 ms. Strict 3072 MiB save-load attempts in BC-capable and no-BC modes stopped before gameplay at 3087–3089 MiB. A 0.30 trial reduced one representative render-target traffic sample about 13%, but frame p95 worsened 0.80 ms and GPU p95 improved only 0.18 ms; this does not support lowering the render-scale floor further or identify resolution as the dominant limiter.

Matched gameplay shows BC-native output clean and no-BC ASTC mode with magenta corruption. A prior no-BC RGBA fallback capture was clean, at higher memory cost. For the candidate 1024²/11-mip BC1 sRGB slot-17 source, the latest gameplay run verifies all 11 GPU-deswizzle/ASTC-transcode outputs byte-exact against CPU. Metal sampling of dumped BC and ASTC payloads across all 11 mips shows at most 1.37/255 error (mean 0.000042 linear; 58 pixels above 1/255 and none above 3/255), zero sampled-alpha mismatches, and exact equality for mip levels 4–10. A follow-up 65,536-point probe uses native BC1-sRGB and ASTC-sRGB textures, randomized repeat-wrapped UVs, explicit gradients, linear min/mag filtering, and trilinear mip filtering across all 11 levels: maximum channel error 0.685/255, mean 0.000380/255, no samples above 1/255 and no alpha mismatches. This makes slot 17's BC1→ASTC representation an unlikely explanation for the large magenta divergence, but the probe does not replay the game's exact shader or inputs and cannot rule out another binding or a render-target/copy issue. The magenta pixels are already observed in a cube render target before presentation. A separate 8×8×8 RG11B10Float-to-2D shader binding `[RED]` remains unqualified.

The requested punch-through-alpha-to-ASTC conversion is incomplete: selector-3 BC1 blocks use lossless RGBA fallback, preserving content but potentially increasing memory. The checksummed disk conversion cache applies only to the opt-in CPU safe-subset branch; the normal GPU-transcode path bypasses it. Category ledgers (guest, alias, Metal, GPU, staging and disk cache) are incomplete or overlapping, so they cannot be added as a partition of process footprint. No candidate allocation should be reclaimed until ownership, reconstructibility and GPU completion are established.

**Tier strategy:** do not ship one preset for all older Apple GPUs. Use native BC as the reference where supported; treat no-BC rendering as diagnostic until image parity passes. Select scale and staging/cache budgets from measured CPU submission, GPU time, actual app memory allowance and upload bursts. Current evidence justifies investigating CPU replay/submission after the correctness gate; it does not justify a validated A16 Pro preset. Sustained frame pacing, thermal and battery claims require user-provided sideloaded A16 device logs.

### Does a 3 GB app memory allowance suffice? (2026-10-26)

**Not demonstrated; current evidence says no for the present build and tested path.** On the Mac harness, two strict 3072 MiB save-load attempts were terminated at 3087–3089 MiB before gameplay. The latest token-confirmed 20-second gameplay routes used a 6144 MiB diagnostic watchdog and peaked at 3789 MiB (BC-capable) and 4887 MiB (ASTC-disabled no-BC); both also missed frame-time and image-correctness gates. These measurements do not prove the physical iPhone's exact jetsam threshold, because Mac footprint, the harness watchdog, iOS process accounting, and GPU residency are not interchangeable. They do show that the current implementation has not qualified for a 3 GB budget, and the strict simulation fails during loading. The 5 GB TOTK guest virtual layout is an address-space design, not evidence that the app receives or can use 5 GB of physical RAM. No claim of playable performance on an A16 device with only 3 GB app memory is justified without reducing/fixing the measured peak and then obtaining real-device sideload logs. The product answer today is **not supported / treat as not playable within 3 GB**, rather than a promise that it will fit.

Latest dynamic keydump follow-up (`01_Great_Sky_Island_20261026T084247_deeea9ae`) added attachment metadata to the targeted trace: the mismatched Product.140 draw writes color attachment c0 serial 2578, 1920×1080, NVN format `0x3f`, Metal format 92; its slot-1 source is the 8×8×8 texture serial 99724. Generated MSL evidence still indicates slot 1 contributes to alpha while slot 0 supplies RGB, so this trace does not establish the source of the scene-wide green cast. Gameplay was visible, but the route lasted only one second; peak footprint was 4714 MiB and frame p50/p95/p99 was 33.63/37.19/388.93 ms (95 samples). This is diagnostic evidence only. Exact source/output raw captures and green-cast causality remain open.

### Texture-memory stress probes (2026-10-26)

The current priority is reducing the measured memory peak. Renderer and image-correctness issues are recorded above, but are deferred until a memory experiment approaches the 3072 MiB budget; these probes are diagnostic and do not qualify gameplay.

On the same Great Sky Island route at render scale 0.5, the baseline no-BC run with ASTC disabled and the existing 2K mip clamp peaked at 4740 MiB. Forcing a source max-side cutoff of 512 px reduced the peak to 3978 MiB (−762 MiB), but still exceeded the budget by 906 MiB. Tightening the cutoff to 256 px reached 3930 MiB, and 128 px reached 3933 MiB: only about 45 MiB more reduction beyond 512, with no gain from the most aggressive setting. The 128 px route's frame p95 rose to 57.37 ms; clamp 128 is not a viable preset.

A follow-up with the safe-subset ASTC converter enabled and the same 512 px cutoff peaked at 3935 MiB, 863 MiB over budget. ASTC stand-ins were 158 MiB and BC decompression 181 MiB; upload staging peaked at 32 MiB. Its 20-second gameplay route completed, but frame p95 was 49.07 ms and save/region-load time 17.09 s. The run's color corruption is not being investigated in this memory phase. These non-identical diagnostic runs suggest that severe mip removal is currently the largest demonstrated lever, while the 512→128 px cutoff has sharply diminishing returns; they do not establish an isolated ASTC savings figure.

A second clamp-512 run lowered the diagnostic watchdog to 4096 MiB so pressure pruning would engage earlier. It reached confirmed gameplay and peaked at 4001 MiB (929 MiB over acceptance), with 486 MiB ASTC stand-ins and 349 MiB BC decompression. The renderer evicted 333 idle packaged textures, shared aliases, and 76 MiB across idle guest pools near the end, yet the run still approached the 4096 MiB watchdog; frame p95 was 52.39 ms and region load took 67.64 s. This shows pruning activates but does not make the loaded gameplay set fit 3 GiB, and adds re-upload/load pressure. It does not justify more aggressive blanket eviction.

The clamp implementation was then changed so `DM_CLAMP_MAX_SIDE` really skips enough top mip levels to keep the retained source side at or below the requested limit. Confirmed gameplay runs with retained-side caps 512, 128 and 64 px peaked at 4106, 3622 and 3614 MiB respectively; 64 px had only 8 MiB benefit over 128 px. A 0.30 render-scale run at a 128 px cap peaked at 4120 MiB, so this non-matched run gives no evidence that lowering render scale reduces the load/gameplay memory peak. After a host rebuild, a 64 px repeat (`01_Great_Sky_Island_20261026T103649_385a858d`) peaked at 3656 MiB, with 1385 MiB guest heap, 1057 MiB guest alias, 2048 MiB peak Metal allocation, 421 MiB GPU ledger, 12 MiB upload staging and 592 MiB unattributed; the gameplay route was confirmed and completed. Frame p95 was 44.74 ms and region load 89.47 s. The small difference from the prior 64 px run reflects route/run variation, not a useful cap benefit. Texture mip loss has reached a practical floor and does not approach 3072 MiB.

The next memory work should attribute guest heap pages, alias backing and Metal allocations by owner/lifetime, then look for data that can be discarded and recreated without shrinking the guest pool or breaking save/load. The current peak is roughly 0.55–0.58 GiB above the Mac acceptance ceiling even with the extreme cap; texture-side tweaks and upload-staging reductions cannot bridge it. Rendering correctness remains deferred per the current direction.

An opt-in allocation-attribution probe (`DM_NVN_ALLOCPROF=1`) on a separate 128 px run, `01_Great_Sky_Island_20261026T104043_ba92894f`, peaked at 3483 MiB, with peak Metal allocation 1842 MiB and the route confirmed. Its rough cumulative Metal-growth attribution ranked `OP_DRAW_IDX` 1987 MiB, `OP_END` 581 MiB and `OP_UPDATE_UB` 401 MiB. The probe samples the operation most recently replayed, while allocations can occur on other threads, so these values do not identify the allocation owner and must not be treated as measured per-op costs. They make draw-time resources, command completion and uniform-buffer updates the next instrumentation targets. This instrumented route's p95 was 35.49 ms; it is a memory diagnostic, not a timing baseline.

### Residency measurement correction (2026-10-26)

The allocation profiler's attribution is weaker than the previous paragraph suggested. Its outer `encode_args` and inner `tex_mtl` samples overlap, and allocations can occur on other threads; the reported operation and function totals are cumulative, overlapping diagnostics, not disjoint owners. The 29,506 MiB gross churn attributed to `res_add` at line 2512 also includes `tex_linear` textures made as zero-copy views over pool buffers. A view's `allocatedSize` can describe shared backing, so that gross sum is not additional physical GPU memory. Under the aggressive 128 px no-BC route, logged BC decompression was 73 MiB and ASTC stand-ins 33 MiB; conversion expansion alone cannot explain the several-hundred-MiB gap in that run.

The watchdog now reports both the existing per-object residency total and a second estimate deduplicated by each texture's root parent or backing buffer, plus view counts. The Mac host build completed with existing compiler warnings. Run `01_Great_Sky_Island_20261026T110427_446cacc7` completed a confirmed 20-second gameplay route at 3612 MiB peak, with guest heap 1172 MiB, alias 906 MiB, Metal 2008 MiB, 12 MiB upload staging, and no simulated kill; the 4096 MiB diagnostic threshold did not trigger the new snapshot. A repeat at 3584 MiB stopped before gameplay at 3593 MiB (frame 5489) and emitted the telemetry: 795 textures reported 13,953 MiB gross plus 404 buffers at 928 MiB, while 62 buffer-backed textures deduplicated to 1,137 root resources at 1,002 MiB. Metal `currentAllocatedSize` at the same crossing was 1,973 MiB. The 1,002 MiB root sum therefore undercounts Metal's total by about 971 MiB and is only a lower-bound estimate for tracked residency, not a physical-memory partition or a reclaimable-byte claim. The run's memstat sample immediately before kill was 3,579 MiB footprint, 1,958 MiB Metal allocation, guest heap 1,104 MiB resident / 1,379 MiB charged, alias 387 MiB resident / 1,057 MiB charged, GPU-tagged 190 MiB resident / 420 MiB charged, and 502 MiB unattributed; VM-region data is a separate sampled view, not additive to these counters. The next memory work is to locate the roughly 971 MiB of Metal allocation not explained by unique roots, then map its lifetime to guest heaps, pools, pipelines and internal resources. The 3584 MiB run is a pre-gameplay diagnostic and does not qualify memory or gameplay; no rendering investigation is part of this pass.

The user asked to explore extreme RAM cuts, so the benchmark now accepts an explicit `DM_APP_POOL_LIMIT_MB` diagnostic override (profile default 3285 MiB). This caps Horizon's application pool and therefore alias mappings; it is not an OS physical-memory limit. With the same save, 0.5 scale and 128 px texture cap, a 2800 MiB app-pool run reached 2883 MiB footprint but alias mapping stopped at 0.58 GiB, `MapPhysicalMemory` was refused, the log recorded `MSF`, and gameplay was not confirmed. At 3000 MiB, alias mapping reached 0.77 GiB, then repeated mapping refusals and two `MSF` markers occurred; the operator later confirmed a gameplay image, but the route is invalid under the no-`MSF` gate. Its peak was 3396 MiB, so this pool cap did not approach 3072 MiB while preserving the memory invariant. Keep the override diagnostic-only; do not lower the game's profile pool. Smaller pool caps trade a misleadingly low pre-gameplay footprint for failed world/resource loading.

No preset reaches 3072 MiB. Continue with the memory ledger and targeted ownership/reclaim experiments (guest pages, Metal textures, alias mappings, staging and caches); do not shrink the game's guest pool blindly, since an `MSF` during play invalidates the result. Keep the experimental clamp opt-in and do not qualify its visibly reduced texture detail as a shipping choice. Revisit renderer correctness after the peak is materially closer to budget.

### Device-tier strategy

Do not assign one preset to every older Apple device. Select the renderer path from detected BC support, the app's actual memory allowance, and measured CPU/GPU/upload time. Keep render scale at 0.5 as the baseline. If GPU time is over budget while CPU submission is not, lower render scale first, then reduce render-pass bandwidth and redundant clears. If CPU submission is over budget, optimize replay, bindings, and pipeline reuse. If upload bursts dominate, bound staging by retained bytes and avoid bulk eviction that causes re-uploads. Keep texture fidelity while render scale can still be reduced; only consider lower texture mips after image review and measured evidence that scale reduction is insufficient. For lower memory allowances, evict reconstructible resources after GPU completion and keep conversion/staging caches bounded; never shrink guest pools by a fixed amount that risks SDK `MSF`. Use the BC-capable Mac run as a reference and no-BC mode for A16-class testing, but do not infer physical A16 thermals or battery behavior from Mac measurements.

The no-BC BC4 render target needs more than reusing the native-BC shadow path. On A16 its base is a decompressed R8 3D texture, and Metal texture views cannot cast a 3D texture to a 2D slice. The host path handles the observed TOTK shape (BC4 `0x49`, RGBA16UI view `0x2c`, 32×32×32, six mips, not COMPRESSIBLE): it deswizzles and seeds every guest mip into an RGBA16Uint 3D raw backing, copies raw blocks into a 2D render shadow, then writes the shadow back to raw storage and decodes the matching R8 depth plane after the pass. Other observed 3D BC4 textures are also initialized from guest mip storage. Unsupported clears, CPU writes, or copies that cannot preserve raw blocks invalidate the backing; attachment remains a missing-draw diagnostic in that state rather than sampling stale data. Other target shapes remain subject to validation.

The BC4 decoder kernel is included in `t_bcastc`. On the current Mac Metal device the fixture verifies an odd-sized 19×17×3 texture and exact CPU parity, plus exact parity across all six mips of a 32×32×32 BC4 texture. BC1-to-ASTC uses an RGB-direct block for packaged textures whose static contents pass a selector scan. Four-colour blocks use the existing four-level weight mode; three-colour blocks without selector 3 use ASTC’s five-level weight mode so the midpoint is represented exactly in the tested black/white fixture. Blocks containing selector 3 remain lossless RGBA8 fallback: selector 3 is black in RGB_DXT1 and transparent in RGBA_DXT1, neither represented by this RGB-direct block. Unreadable/sparse sources, dynamic textures, failed scans, and other BC formats also retain exact fallback. The source format selects linear or sRGB ASTC, and the disk cache key/revision was bumped for the changed block encoding. Metal readback reports maximum RGB error 2 for the randomized four-colour fixture, exact RGB for the tested three-colour midpoint fixture, and no alpha mismatch; a selector-3 fixture is explicitly rejected by the ASTC-safe classifier.
